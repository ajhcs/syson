# F27: isolated selected-document SQLite candidate

This crate persists selected `syson_model::Document` JSON through one bounded SQLite adapter. It does not apply the F26 Liquibase declarations or implement the native PostgreSQL schema. The inherited resource-to-document and serializer SPIs, exact deployed artifacts and native transaction/event correspondence remain unresolved. Eleven source pins retain those boundaries and the F25/F04 APIs actually consumed.

The key has separate project and document UUID bytes. Neither replaces the JSON node `id` or SysML `elementId` inside the content. All model content is serialized in Rust, transported as a string and stored as TEXT; the Python bridge never parses or normalizes the document JSON. Reload revalidates the selected JSON envelope. The tests use the actual F04 registry to prove a local reference still resolves by JSON node identity, with no semantic-ID fallback, and distinguish equal document/element IDs in two projects.

`Store::create` requires an explicit fresh absolute path and uses create-new admission. `Store::open` and all later reads/writes use SQLite URI mode `ro` or `rw`, so a missing database is not silently created. The private bridge checks application ID, version and exact retained SQLite table declarations before mutations. Candidate schema identity is a format check, not an attestation that an external file is trustworthy or an authorization boundary. A file is never selected by discovery, URL or environment default. The caller owns its path and lifecycle; an initialization failure retains the newly created file for diagnosis.

Each mutation batch uses `BEGIN IMMEDIATE`, fixed parameterized statements and one commit. Stored read-only flags and expected revisions are checked inside that transaction. Duplicate, stale, missing or read-only refusals roll back all earlier operations. Read-only is a conservative local document policy, not proof of the native object/library policy or project permissions. A database-global transactional clock prevents delete/recreate from making an old observation valid again. Store-handle tokens also reject observations from another handle. Concurrency qualification is limited to SQLite revision/lock behavior exercised by the tests; no power-loss, cross-host, multiprocess stress or distributed acknowledgment guarantee is claimed.

Updates call the real F25 `plan_documents` for one existing/incoming document. Equal ID/name/content keeps the existing row and revision; a changed name/content follows its rebuild decision and clears the row's read-only flag after the stored write policy permits the operation. Source timestamps, domain collection changes, dependency mutation, aggregate clocks and event publication are outside this adapter. The local revision clock is not a substitute for a native `Instant` or event identity.

The adapter invokes `/usr/bin/python3 -I -S -B -c <compiled bridge source> <absolute DB path>` with cleared environment and bounded JSON stdin/stdout. It uses the existing standard-library `sqlite3`; no Rust driver dependency, Python package installation, service, network connection, credential or shell is introduced. SQLite lock timeout is one second, temporary storage is memory, and journal files remain beside the explicitly owned DB. Limits are 64 operations, 1 MiB per serialized document, 8 MiB protocol input/output and 4096 bytes per document name. No arbitrary SQL command is exposed.

A bounded `Write` implementation is passed to the real `serde_json::to_writer`. A document-budget failure is an actual serializer I/O error and occurs before opening SQLite for the batch. The serializer test therefore proves pre-SQL atomic refusal; separate late duplicate/stale/read-only tests prove actual SQL rollback. These are deliberately separate claims.

Tests require coordinator-provided absolute workspace `TMPDIR`. Each creates a fresh retained `f27-test-<pid>-<counter>/store.sqlite3` there; there is no `/tmp` fallback, auto-deletion or production target. Runtime commands and source/execution hashes are recorded only after coordinator approval and execution. `check_sources.py` is a source-only check and never executes the bridge.

## Executed qualification

The coordinator-approved `f27-01` capture passes thirteen integration tests, formatting and scoped Clippy. The eleven pinned-source checks also pass. [VALIDATION.json](VALIDATION.json) and [the original execution receipt](validation/f27-01/receipt.json) preserve exact commands, inputs, tool fingerprints and retained external DB hashes. Independent source-only review found no blocking issue in the finite candidate scope. No native PostgreSQL/application, security or crash-durability acceptance is implied.
