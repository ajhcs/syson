# P01: lexical line comments

Ordinary `//` notes now end at LF, CR, CRLF or EOF in the finite package/part adapter. Scanning uses the original source, preserving quoted slashes, escaped quotes and raw byte/UTF-16 locations. Notes do not spend visible tokens; their bytes still count toward the original source limit. The exact `//*` overlap remains unsupported pending P02, and `/* ... */` remains semantic input pending P05.

Root verification passed 19 integration tests (13 inherited, 6 new), formatting and scoped Clippy on unchanged source. The first attempt, `p01-01`, failed because an inherited unsupported whitelist still included the newly supported line-comment family. Only that entry changed to the still-unsupported multiline-note prefix. Its original source and streams are retained; its new test binary and Clippy were not run. The `is_multiple_of` spelling was preventive, not an observed lint failure.

Ten fresh exact-byte fixtures were observed in both the pinned embedded native CLI and the real Rust adapter. Six selected class/name projections match. The remaining four differences are explicit in [the comparison](differential-analysis.json): native semantic Comment and hidden multiline-note support, recovered/truncated native output for a missing brace, and native ReferenceUsage nodes outside this finite Rust family. Prepared predictions that the last two would produce native refusal were wrong and remain unchanged in [the original packet](fixtures.json).

Native `dump --stdlib none` checks `document.diagnostics`, and this path builds with `validationChecks: none`; an exit-zero AST does not establish the absence of parser recovery. Native dump reference parts may already contain cleaned, resolved, qualified names; the Rust arena preserves raw unresolved segments. Rust spans were checked against original source bytes and UTF-16 counts, not against native offset metadata. This is not full AST, native application, editor, performance or whole-language parity.
