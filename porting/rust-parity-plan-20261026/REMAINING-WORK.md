## Completion requires these distinct decisions

A scope is **ready to implement** only when its required implementation inputs, review budget, interface and nonoverlapping ownership are admitted. A scope is **locally verified** when the exact source passes its named checks; this does not establish native equivalence, integrated UI behavior or durability.

A PR is **landed** when the reviewed change and actual prerequisites are on main, affected checks/callers apply to the resulting composition, and the remote landing tree is verified. A feature is **accepted** only when every required source obligation has an independently reviewed runtime disposition, including applicable native, consuming-workflow, failure, UI and resource evidence. An intentional UX improvement needs its behavior record and compatibility impact; it cannot erase a mismatch by permissive normalization.

The program is complete when C01's required scope is closed; every primary and discovered obligation is accepted on one target/candidate closure; connected workflows, interoperability, recovery, usability and capacity gates pass; and clean release rebuild, packages/processes, notices and upgrade/rollback evidence are accepted. Required unsupported, unresolved, unimplemented or unrun work prevents completion. Unchanged-component evidence may be reused only with explicit unchanged-input proof; affected/composed workflows must cover the final candidate.

For each completion decision, retain the source/artifact revisions, requirement and case IDs, commands, raw results, differences, failed attempts, independent review, remaining limits and resulting GitHub main tree. Name any required unrun platform or workflow explicitly. A plan lock proves document integrity; it does not close a feature.

The current completion checker validates planning structure and evidence bindings; stronger behavioral enforcement remains RR16b/RR17 work. An expected `OPEN` result is an honest status check, not a completed program. Review or amend this snapshot deliberately when priorities or progress change; requirement changes continue through the versioned completion-contract process.
