# Remaining SysON parity work: delivery order and completion criteria

We have landed useful Rust foundations, but we have not completed SysON feature parity. The next product milestone is a connected Rust project workflow: create or import a project → edit → save → reload the page → close and reopen → restart the backend → inspect from a fresh connection. The committed model and representations must survive every step without manual JSON reimport. Semantic, language, library and view work continues in parallel wherever dependencies and ownership permit.

For each remaining scope, this plan identifies the change, the prerequisites, the source owner and the evidence required for completion. The [780-entry task register](remaining-work/units.json) retains every adopted task, dependency, ownership path and acceptance condition. The priorities below schedule that scope; they do not reduce it or imply that 780 PRs remain.

This is the locked execution guide for the existing **SYSON-RUST-COMPLETION/1.0.2** contract, frozen against main `af4c5844819b9a0314d5f8bdbb68ae284c207277` on 2026-10-29. The [version 1.0.2 amendment](amendments/1.0.2-rr08-split.md) preserves the original 778 obligations and adds RR08a/RR08b as sequential execution children. Each retains the ordinary 400 changed production / 900 authored line caps; the complete parent repair and acceptance gates remain required. The earlier F10/F11 budget dispositions remain unchanged. The [snapshot lock](remaining-work/snapshot.lock.json) binds this guide and the complete task register to their source inputs. Changes to requirements still require the contract's versioned review process.

## Deliver the first durable Rust workflow

The first application milestone spans B02/B03/B05/B06/B07/B08/B23/B27/B28/B31 and U01/U03/U04/U05/U07 with their declared dependencies. Split the work by the existing briefs rather than making one large “persistence” PR.

1. **Host and project boundaries.** Connect the actual Rust session, project and command paths. Verify isolation between projects and clients, stale versions, read-only resources, cancellation and truthful errors.
2. **Storage and migration.** Persist semantic data, representations, metadata and migration watermarks atomically. Integrate B01's preparation through B06's real load/save transaction. Replace the Python SQLite application bridge under B07 before claiming the Rust delivery target.
3. **UI create/import/edit/save.** Use real events through the Rust application. Commit a Package name, save, reload the page, close and reopen the project. The committed result must return without manual import.
4. **Restart and recovery.** Restart the backend and inspect through a fresh connection. Inject failure before, between and after writes, cancellation around commit, stale compare-and-swap observations and lost acknowledgments. A success represents the required durable state; a failure retains the previous committed project and offers truthful recovery.
5. **Download and fresh reopen.** Inspect the actual downloaded bytes, reopen them in a fresh context, and compare identities, references, representations, revisions and migration state. A round-trip helper alone does not satisfy the UI/storage journey.

Keep the batch13 long-name counterexample: `Long <&> 雪🧭 ` + 4096 `x` characters + ` END` (4,113 UTF-16 units; 4,117 UTF-8 bytes). Native SysON retained it after save/reselect/page reload; Rust required explicit reimport. The 4,442-byte Rust export/reimport remains bounded evidence. Page reload and backend restart are separate gates, and the native artifact's source gap still limits parity claims.

This milestone closes only when its connected callers and failure cases pass on the integrated candidate. It does not complete all persistence, API, model or language obligations.

## Verify each PR and keep the evidence useful

Use one isolated worktree and `codex/` branch per PR, with at most three source authors and one coordinator. Aim for at most 400 changed handwritten production lines and 900 authored lines including tests. Preserve an already approved exception explicitly. Split broader work into reviewed child IDs before coding; never invent a child only after exceeding the budget. Shared manifests/locks, crate exports, routes, registries and application assembly belong to the coordinator. Existing raw/factory/initializer and validation holds remain in force until explicit handoff.

Each PR normally has an implementation/regression commit and a separate evidence/disposition commit. Add an earlier contract/fixture commit where the source boundary is new. For a repair, reproduce the failure where feasible; retain the old failure when the fix passes. Before merging, check the exact reviewed diff, current prerequisites, review threads, hosted check status and expected head. Verify the resulting main tree afterward. Report absent hosted checks as absent, not as a CI pass.

Run focused formatting, locked/offline tests, all-target Clippy and applicable native/WASM checks with one compiler job and one test thread. Bind source before/after, tools, fixtures and external inputs to the receipt. Exercise real downstream calls. Browser evidence requires real events, meaningful rendered content, screenshots, focus/accessibility state, console/page errors and resulting model/history/representation artifacts. Tests and screenshots support their named cases; they do not alone establish usability.

For changed performance paths, use release builds and restore identical model, selection, drafts and history between repetitions. Record two warmups and seven measured samples per named action/viewport, with all raw values and min/median/max. Use at least 30 measured samples and a declared estimator for p95. Keep event-to-visible latency, main-thread tasks, server/database time, allocation requests, peak live heap and RSS separate. Compare equivalent native/Rust workloads before making speed claims.

## Completion requires these distinct decisions

A scope is **ready to implement** only when its required implementation inputs, review budget, interface and nonoverlapping ownership are admitted. A scope is **locally verified** when the exact source passes its named checks; this does not establish native equivalence, integrated UI behavior or durability.

A PR is **landed** when the reviewed change and actual prerequisites are on main, affected checks/callers apply to the resulting composition, and the remote landing tree is verified. A feature is **accepted** only when every required source obligation has an independently reviewed runtime disposition, including applicable native, consuming-workflow, failure, UI and resource evidence. An intentional UX improvement needs its behavior record and compatibility impact; it cannot erase a mismatch by permissive normalization.

The program is complete when C01's required scope is closed; every primary and discovered obligation is accepted on one target/candidate closure; connected workflows, interoperability, recovery, usability and capacity gates pass; and clean release rebuild, packages/processes, notices and upgrade/rollback evidence are accepted. Required unsupported, unresolved, unimplemented or unrun work prevents completion. Unchanged-component evidence may be reused only with explicit unchanged-input proof; affected/composed workflows must cover the final candidate.

For each completion decision, retain the source/artifact revisions, requirement and case IDs, commands, raw results, differences, failed attempts, independent review, remaining limits and resulting GitHub main tree. Name any required unrun platform or workflow explicitly. A plan lock proves document integrity; it does not close a feature.

The current completion checker validates planning structure and evidence bindings; stronger behavioral enforcement remains RR16b/RR17 work. An expected `OPEN` result is an honest status check, not a completed program. Review or amend this snapshot deliberately when priorities or progress change; requirement changes continue through the versioned completion-contract process.
