# SysON feature parity in Rust: implementation and verification plan

This plan targets Eclipse SysON source `6ba2ac64e6b16ee2b05752ad55395eebb87d4910`. It carries the 33-unit audit forward into a complete application program: semantic runtime, parser, persistence, APIs, views, browser interactions, interoperability and acceptance. The [PR index](PR-INDEX.md) links an individual task and verification brief for every named review unit. [plan.json](plan.json) is the normalized dependency graph; [dispatch.json](dispatch.json) gives bounded potential author waves. Lane snapshots preserve exact source selections and larger source-assignment tables.

The plan is executable and detailed for the currently inventoried work. The inherited runtime/source closure is still open. C01 must resolve that closure and add any discovered behavior as small named child PRs before final acceptance. The initial PR count is therefore a review schedule, not a promise that no additional work will be found. Assigning a source candidate to a PR is not implementing or testing it.

The initial expansion contains **720 named review units**: 408 model/reference units, 184 parser/text units, 45 platform units, 73 browser/diagram units and ten coordination/verification units. This includes small source-derived implementation batches, construction/behavior qualification batches and acceptance gates. Adjacent already-implemented obligations can be consolidated into a coherent verification PR within the review budget; newly discovered behavior must receive additional child IDs. The count is not an estimate of completed features or a fixed final number of GitHub PRs.

## Starting point and target

The audited 33 units comprise five source-preparation packets, 15 algorithms, 11 bounded backend adapters and two direct browser surfaces. Eight audit repairs are draft PRs #58–#65; the report is [#66](https://github.com/ajhcs/syson/pull/66). Most backend adapters are not connected to the default editor. The existing 47 briefs remain historical planning inputs; their 14 unimplemented units are mapped in plan.json rather than silently dropped or counted complete.

The previous native run used the official 2026.9.3 artifact with source label `b380dada415ce05155150f23cb3b74ae21cc45e4`, which differs from the target by 125 source paths. Its observations remain useful but cannot close exact-source parity. C01 establishes the matching artifact/source closure. The pinned Syside CLI hash is `47d8fe11fda1b58b6257463087f663be953c2ab6c2b5e1e2ccc44161ed5cd0bd`; source-candidate Sirius and Syside revisions also require artifact correspondence. All evidence records the actual revision used.

Feature parity means the same supported user task produces compatible semantic, reference, API, persistence and observable interaction outcomes on matched inputs. It includes malformed and unsupported inputs, cancellation, stale responses, read-only state, errors, recovery, ordering, Unicode and lifecycle behavior. A Rust algorithm, generated declaration table, screenshot or passing test count alone does not complete a user feature.

## Rust production architecture

All authored application behavior is Rust: model and semantic services, lexer/parser/CST/AST/linker/validation, server and transport adapters, persistence and migrations, view descriptions, layout/routing, project/session/history and browser interaction state. Native server executables and browser WASM share typed Rust contracts, while retaining independent project, resource, node, semantic and representation identities.

The browser may use generated WASM loading/binding glue. It must contain no handwritten application decisions, event-state machine, layout policy or hidden React/Sirius/Apollo/Xyflow implementation. U01/U02 replace the current loader.js behavior in ordered families. The Rust host uses reviewed, pinned Rust transport/database dependencies. B07 replaces the existing Python SQLite bridge; shipping it or a Node/Syside/Java fallback does not meet the target.

Browser engines, PostgreSQL and explicitly declared lower-level native libraries are platform dependencies. They are not application-code ports. Record their provenance and languages in the release closure; do not conceal them behind a “Rust-only” label. Development-only Java, Syside, TypeScript, Playwright and Python tooling can run the upstream oracle or validate artifacts, but are excluded from the production application dependency/process closure. C04 and B32 prove that boundary on actual distributed artifacts and live processes.

Public Rust APIs must distinguish unresolved, unsupported, malformed, cancelled and failed results. No semantic-ID/node-ID guessing, silent URI loading or partial mutation is allowed. Schema compatibility and improved UX must coexist: intentional differences get a named behavior record, source/native observations, compatibility impact, objective benefit and independent review. Never erase a mismatch through permissive output normalization.

## Milestones and critical path

1. **Reference and assembly foundations.** C01 closes the native/artifact/inherited capability inventory; C02 and C04–C09 establish typed differential fixtures and runtime comparators; C03 coordinates exact existing PR composition. The first P01/I01/B01 batch can use its already frozen, local source contracts while this broader closure proceeds. These bounded units do not imply C01 completion.
2. **Semantic and language closure.** Model/reference families implement resource identity, inverse/derived/cache/proxy behavior, all admitted constructors, import visibility, libraries and semantic operations. Parser families implement the remaining grammar/AST/linking/import/export/diagnostic/recovery obligations. Generated metadata is reviewed separately from handwritten semantic methods. Held F06/F07 work remains gated on its existing owner's explicit handoff.
3. **A durable connected Rust application.** Rust host, session/project boundaries, atomic semantic/representation/metadata storage, commands, subscriptions and history support a real project lifecycle. U03–U08 connect project creation/loading, explorer, details, text import, validation and real file export/reload. Completing DTOs or a pure migration preparation function does not complete this milestone.
4. **All effective views and tools.** Rust General, Interconnection, Action Flow and State Transition views, requirements table, details, explorer, validation, query, related elements, library/publication and active inherited view families run actual semantic services. The concrete provider PRs assign exact source files in small batches. Every effective provider method still needs its positive, negative and real UI dispositions.
5. **Capacity, usability and interoperability.** Matched native/Rust journeys exercise both interchange directions, cross-resource IDs, libraries, project archives and applicable upgrades. Keyboard/speech/touch/zoom/contrast, representative engineer tasks, cancellation and performance evidence qualify the assembled application. Prototype limits are removed through measured bounded implementations.
6. **Parity and release closure.** Every inventoried required behavior has an accepted runtime disposition; no required unresolved, unimplemented or unrun entry remains. Final clean-tree build, notices, package/process audit, migration/recovery and composed workflow evidence refer to the same release candidate. Production deployment remains a separate action.

New-plan dependency edges in plan.json are authoritative for scheduling. Existing PR dependencies retain their frozen heads and snapshot bases until reviewed landing/retargeting. Cross-lane UI/service edges and provider prerequisites are added explicitly by the coordinator; original lane snapshots remain immutable for provenance.

The index, source prerequisite lists and dispatch waves describe **source preparation**. A draft adapter can be prepared against a frozen interface before its semantic implementation exists. **Implementation readiness** additionally requires the named implementation_ready_dependencies and local behavior checks. **Feature acceptance** requires the actual runtime/native/UI evidence, acceptance_children and acceptance_gates. Joint gates consume implementation-ready callers and every semantic child in their transitive dependency closure, avoiding reciprocal acceptance cycles. C99 waits for every other unit's accepted state. None of these stages can be replaced by a published-draft label.

## PR size, ownership and commits

Each unit owns one behavior family. Aim for at most 400 changed handwritten production lines and 900 authored lines including tests. A generated table, source assignment or retained execution receipt gets its own evidence commit and is reviewed for generation correctness. If a source provider, grammar family or API schema group exceeds the budget, freeze named child IDs, dependencies and acceptance cases before coding; do not bury a broad implementation under a small-PR title.

Use one isolated worktree and `codex/` branch per PR. An author edits only its leased module/tests; one coordinator serializes shared Cargo manifests, locks, crate exports, route registration, default application assembly and generated registries. Never give two authors the same common file. A source-author wave is not permission to run concurrent compilers, databases, browsers or upstream application builds.

Typical commits are (1) exact contracts/fixtures when a new source boundary is involved, (2) implementation plus meaningful regressions and caller integration, and (3) evidence/disposition. A small already pinned repair can use implementation/tests plus evidence as two commits. Keep unrelated fixes in separate PRs. Preserve all original failed attempts and their exact inputs. Do not relabel an old capture after changing code or a fixture.

At dispatch, read current branch/head/status, source ownership, held scopes and prerequisite PR metadata. Confirm Samsung workspace identity and the approved resource allocation. Use fixed synthetic inputs and fresh owned paths. No source work may change the existing factory/model/initializer holds merely because an owner appears idle. Record the missing handoff as a dependency; continue independent work.

## Execution procedure for every PR

1. **Freeze.** Read the unit brief, effective source and inherited services. Enumerate source methods/features/rules and observable cases. Record exact base/snapshot, tool hashes, dependency locks and source input closure. Inspect new dependency manifests, build scripts and runtime side effects before executing them.
2. **Establish evidence.** For a repair, reproduce the failure before patching when feasible. For a new feature, capture the matched native fixture before writing a permissive expectation. Retain raw streams and negative outcomes. A recovered parser AST is not proof the native application accepts that model.
3. **Implement.** Keep identity and transaction boundaries explicit. Use the actual downstream caller/model/importer/registry rather than a mirror implementation or mocked success path. Add only tests that protect observable behavior, risk boundaries or meaningful performance characteristics.
4. **Run focused checks.** Formatting, offline/locked compilation/tests and all-target Clippy run with one compiler job and one test thread under coordinator ownership. Add native/WASM target checks when the changed dependency reaches them. Capture source before/after and refuse source drift. Run only the necessary changed or still-unexecuted remainder; broaden checks when new failures or changed dependencies justify it.
5. **Run relevant runtime checks.** Use actual public Rust transport/storage/UI paths and matching native fixtures. Disposable SQL state is operation-reviewed and separated from source. Browser evidence must include real event dispatch, meaningful nonblank UI, page/console errors, focus/AX state, screenshots and model/history/representation artifacts. No direct handler call substitutes for a GUI journey.
6. **Measure.** Use release builds, fixed datasets, repeated samples and actual process RSS excluding compilation. Separate compute, request, database, browser-paint proxy, startup and presentation metrics. Keep raw ranges; do not compare unmatched native/Rust workloads or count observed absence of a long task as zero CPU work.
7. **Review.** An independent agent inspects the immutable diff, contracts, executed input hashes, failure retention and limitations. The reviewer does not overwrite an author's evidence. Resolve concrete findings, freeze new inputs and execute only checks justified by the change.
8. **Publish.** Verify committed blobs match executed bytes, clean author worktree and released lease. Push and create one draft PR with exact prerequisite/base, before/after behavior, validation and residual scope. Read it back. After prerequisites land through repository review, retarget, inspect and revalidate the actual composition. Never merge a child into a feature prerequisite or temporary snapshot.

## Verification matrix and target ranges

Targets below are proposed project acceptance criteria. Prior audit measurements apply only to their recorded small workloads. New-family PRs must fill their own cases and native/composed observations.

| Area | Required cases and evidence | Gate |
|---|---|---|
| Model and references | Every source feature/operation; inheritance/opposites/derived/unset/cache/proxy/notification; local/cross-resource/unknown/read-only; same-class node/semantic UUID collisions | Compatible identities, ordering, values and failure behavior; explicit unsupported residuals block required parity |
| Parser and semantic text | Every grammar/terminal/AST hook; accepted/rejected/recovered syntax; Unicode/comment/escape/span/forward/import/alias/expression/validation families | Actual AST/model/link/export-reload differential, not recognizer acceptance or class/name projection alone |
| API and sessions | Effective REST routes and GraphQL fields/inputs/unions/errors/subscriptions; missing/stale/forbidden/malformed/oversize/cancel/reconnect | Actual wire contract and observable state compatible; two project/client contexts cannot cross their qualified boundary |
| Persistence and migrations | Fresh CRUD/reopen, revisions, atomic semantic+representation+watermark changes, prior-version fixtures, rollback and replay | No partial publication or double migration; native schema/project-format policy and restore proven separately from local SQLite |
| User workflows | Project/template, every view/tool, details, text/errors, file/archives, library publication, history, query/navigation and reconnect | Actual user action reaches semantic command, persistence and reopen; invalid operations retain drafts and committed state |
| Responsive UI | 320/390/640/1365/1440 CSS px, empty/loading/populated/error/read-only/pending, 200/400% zoom | No page overflow or unreachable controls; primary targets at least44 by44px; readable diagram zoom/scroll alternative |
| Accessibility | Keyboard-only tasks, focus/caret/disclosures, accessible names/live states, contrast and real screen-reader speech | Evidence includes inspected screens, AX tree and actual speech/task observations; no automated-only certification claim |
| Small edits | At least30 matched select/stage/cancel/commit samples on fixed host/browser | Proposed p95<=100ms; report p50/p95/max and task definition |
| Bounded diagram | At least30 real requests on32nodes/64edges, multiple shapes/fonts/labels/cancellation | Proposed p95<=250ms and no computation task>50ms; preserve input responsiveness and raw timings |
| Large/capacity | Documented10MB model,150000 semantic elements,2000 representations/project,1000 elements/representation,1000 projects and80 concurrent users | Treat native documentation as hypotheses to measure, not guarantees. Stage resource-reviewed ramps; compare matched versions/hardware and keep any unmet capacity open |
| Lifecycle/performance | Cold/warm startup,1k/5k/10k query/reconciliation, repeated mount/import/reconnect and memory | Bounded allocation and listener/process counts; document dataset/environment; fix measured bottlenecks in separate PRs |
| Rust distribution | Actual executable/WASM/assets/dependency/process closure and clean rebuild | No shipped Java/Node/Python semantic fallback or handwritten JS application logic; complete applicable notices and declared native/platform dependencies |

Current prototype admission limits are deliberate safety boundaries, not native-capacity acceptance. U29 and the responsible model/parser/storage units raise them only with measured allocation/backpressure and recovery. Native documentation claims, semantic element counts and representation element counts use different definitions; fixture manifests must state exactly what is counted.

## Completion accounting

The first batch is published as [P01 #68](https://github.com/ajhcs/syson/pull/68), [I01 #69](https://github.com/ajhcs/syson/pull/69) and [B01 #70](https://github.com/ajhcs/syson/pull/70). These implement lexical line comments, reverse native-reference conversion and selected versioned migration preparation. Each has an existing frozen source prerequisite and disjoint production path. B01 prepares immutable outputs; durable all-document/representation/watermark publication is a later storage transaction PR. P01 does not discard semantic block comments. I01 does not guess identity domains.

Statuses distinguish planned, authoring, source-reviewed, locally verified, native-differential verified, composed-workflow verified and accepted. Published draft is a publication state, not feature acceptance. [execution.json](execution.json) records actual first-batch progress without rewriting the planning baseline or historical audit captures.

Run `python3 tools/verify_plan.py --self-test` from this directory to check source and staged graphs, assignment owners, immutable fragment hashes, all 14 original remaining briefs and negative gate examples. Run `python3 tools/verify_plan.py --check-completion` to inspect the acceptance ledger. Exit 2 means parity remains open; this is the expected current result. The checker validates evidence structure and hashes; independent behavioral review is still required.

To regenerate the coordinator-owned UI/source batches, run `python3 tools/build_ui_plan.py --source-root /path/to/frozen-integration-checkout`, then `python3 tools/build_plan.py`. The source-root argument supplies the pinned component inventories absent from a documentation-only plan branch. Regeneration must reproduce the normalized plan and briefs byte-for-byte; lane snapshots change only after a separately reviewed source-assignment update.

Final parity requires all primary obligations and discovered children to have evidence for the target revision. Allowed terminal dispositions are native-compatible behavior, independently justified intentional improvement preserving required compatibility, or source/runtime-proven absence from the native baseline. A required behavior marked unknown, unsupported, unrun, candidate-only or preparation-only prevents completion. The ledger validator must enforce this before any full-parity claim.

All work stays in isolated Samsung workspace worktrees and build paths. Existing dirty work, original source history, failed receipts and held owner scopes remain preserved. Production installation, service registration, destructive state changes, merges and deployment are distinct reviewed actions; passing development checks does not perform them.
