# RR11 SQLite database-generation fencing

A Store now pins a persistent v2 database generation. All later load/create/update/delete requests carry it; the bridge checks schema, generation and row state on the actual opened connection inside the same read or IMMEDIATE transaction. Replacing a pathname with independently created B cannot authorize A's stale observations even when keys and revisions match. Existing handle identity, row CAS, read-only and batch rollback guards remain.

Format v2 adds a singleton random 16-byte generation table. v1 is explicitly refused unchanged; there is no implicit upgrade. Normal reopen keeps the epoch, while explicit `Store::open_restored` renews the restored epoch atomically and invalidates prior handles, including create-only batches. Callers must quiesce writers for offline file replacement/restore. Unannounced same-epoch byte rewinds and live file swaps after a connection is open are unsupported. This is the selected local SQLite candidate; B07 replaces its existing Python bridge with Rust later. It does not establish native PostgreSQL or complete Rust distribution parity.
