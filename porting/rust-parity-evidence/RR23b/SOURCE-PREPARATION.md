## Reader and typed behavior

There is one production Value deserialization boundary in `project(bytes)`. It now uses RR24a `parse_with_duplicate_keys(..., LastWins, ...)` and `into_value`, with no generic Value preparse or marker-name guessing. LastWins preserves the existing final-value duplicate policy, including escaped-equivalent keys. The native PostgreSQL JSONB producer already emits unique object members; this compatibility policy governs supplied reader input, not a new capture claim.

Every accepted catalog slot has a strict shape. There is no accepted arbitrary opaque-object payload: Number/RawValue-named objects in OID, flags, strings, arrays, capture, schema or root slots must refuse rather than be reinterpreted as a valid typed value. Marker-named JSON appearing *inside SQL/default/comment strings* remains exact literal text. All required fields, OID widths, identities, table/column/index/FK links, history positions, nonempty history, scope flags, canonical named obligations and output-counter rules stay in the existing validator.

Pinned arbitrary_precision Number `as_i64` accepts the exact token `-0`, while the original standalone decoder classified that token as floating point and refused it in `orderexecuted`. The final guard explicitly retains that signed-integer refusal. Decimal/exponent forms and out-of-range signed/unsigned/OID values also remain refused. Accepted canonical i64 MIN/0/MAX and u64 MAX metadata controls preserve exact tokens; arbitrary enormous numeric values are *not* promoted into valid typed catalog observations. No numeric normalization is added.
