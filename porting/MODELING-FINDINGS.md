# Reusable modeling findings from the pinned SysON investigation

These are source-grounded observations, not accepted product requirements or complete SysML conformance results. Baseline SysON6ba2ac64e6b16ee2b05752ad55395eebb87d4910 and inherited Sirius source candidate3191e2b8990373afee3415f6b26f8c5039a28321 remain distinct from resolved runtime artifacts.

- Resource-object `id` and semantic `data.elementId` are separate identities in actual EMF JSON. Flat REST `@id`/`@type` representations are another schema. The model adapter preserves both IDs and unknown JSON values; a successful local JSON roundtrip does not prove EMF loading or REST equivalence. See domain/MODEL-ADAPTER.md and the exact SQL-derived fixture.
- Semantic owned elements are derived through all owned Relationships. A generic container tree, membership-only flattening and SysML ownership are different graphs. The original query projection explicitly requires an adapter; the new EMF document projection flattens all contained ownedRelationship objects. External references, inherited names and imported scopes remain additional obligations.
- The executable ElementImpl.getQualifiedName differs from its commented specification: declared/effective names govern qualification; unnamed owners stop prefix construction, and short names do not silently replace absent qualified-name segments. Name lookup preserves first-owned-match/type-shadowing and public-import fallback boundaries. Actual implementation and standard intent require separate evidence.
- Name compatibility includes Java-specific whitespace, UTF16 length and optional quoting behavior. Rust standard Unicode whitespace trimming changed observable results until corrected. Name-conflict filtering mutates its reservation set before later short-name checks fail; rolling back that state would change upstream behavior. These are regression-worthy source quirks, not endorsed naming policy.
- Stable standard-library UUIDv5 computation depends on the precise OMG base URI and qualified name. Resource URI prefix/substr predicates in migration are permissive source checks, not general URI validation. Runtime migration also needs resolver class checks and no-load lookup behavior; string replacement alone is insufficient.
- Ecore declares182domain classifiers, consisting of175classes and7enums, plus4separate custom-node classes. All70declared operations,57parameters,309subset/redefine annotations and19enum literals must remain visible. Generated schema/type metadata does not implement handwritten operation bodies, derived values, constraints or subsetting/redefinition semantics. For example Ecore Feature.isComposite defaults false while a usage initializer sets true.
- Upstream project versioning synthesizes a single branch/commit per project. Documentation about no additional commit history does not mean the inherited createCommit service cannot mutate model objects: the inspected source performs deletion, creation, deserialization and root attachment. That source finding still requires resolved-dependency and runtime verification; source candidate identity is not artifact proof.
- Textual import is a semantic parser dependency: the pinned application invokes an embedded Syside JavaScript bundle through Node. It cannot count as a Rust implementation or be treated as generated loader glue. Source grammar, linking, validation, builtin libraries and exact bundled notices need separate replacement/provenance evidence.

Independent source/native regressions verified the bounded whitespace/selection/migration/transaction findings. UI browser smoke verified selected user flows only. No complete modeling semantics, parser, engineering acceptance, cross-product integration or production readiness is inferred. These findings may inform separate systems while this fork and its implementation remain isolated.
